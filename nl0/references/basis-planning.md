# Planning a foundation reduction

Start from the selected target and original hypotheses. Sketch the whole argument and identify which nontrivial result each consumer needs. Record the type, domains, uniformity and actual use at each consumer. Routine arithmetic and logical background can stay implicit.

1. Locate a declaration in pinned Mathlib (class 1) or a public, revision-identified Lean library (class 2). Retain the source as evidence. Port the smallest useful proof into the pinned environment. A public package name or an extra import does not supply a proof.
2. For a derived fact (class 3), write its mathematical route down to 1/2 or previously derived facts. Give a stable B identifier to a shared obligation. For the remaining hard items use `investigate_basis_frontier` with their statements and consumers. Each worker may search for a declaration, unpack the textbook argument, or propose a specialization and account for every consumer. An unavailable source or a tool failure remains open.
3. Compare the returned routes globally. Prefer a shared fact once when its hypotheses fit all applications. Separate independent conclusions with stable types. Keep a witness and its dependent obligations together when splitting them would obscure the argument. Save candidate routes before selecting the final graph.
4. In the selected global graph, each proposition has an ID and statement. Each inference lists its actual input proposition IDs, one output and the B IDs it directly uses. Original H may be unused. Every derived proposition must contribute to P. A transitive foundation used only in other foundation proofs has no public port. A direct prepared class 2/3 has an E port and a checked discharge.
5. In a planning draft, give each selected class 1/2/3 a complete closed Lean type. Supply an existing proof body or set `lean.proof` to null. `prepare_basis_graph` removes unused alternatives and assigns the missing proofs to isolated workers. Save, check and submit by candidate number. An accepted registry contains checked bodies for every selected 1/2/3. Each private worker sees its frozen statement, declared direct dependencies and route, can build auxiliary lemmas incrementally, and returns source. The controller composes the actual dependencies and checks the complete source again.
6. Keep a residual class 4 only with a precise statement and verified source. If missing proofs still need workers, the residual goes to a separate reviewer and the operator before those workers launch. Stop ends the case, continue returns the plan for further reduction, and accept-conditional binds the exact residual and route. Downstream graph revisions under the same approved foundations keep this decision. A new residual premise requires a reviewed basis revision and an operator decision. The final basis correspondence review and final kernel discharge still apply.

Prefer targeted source reads and small source extracts. The controller bounds individual downloads and shares a requested readable URL within its case. Every role gets an independent file view. Disk pressure is an execution fault. Preserve accepted evidence and retry after sufficient space becomes available.

Write each proposition in the global graph as a standalone mathematical statement. Put proposition IDs in inference input and output fields. The editable basis producer applies the same prose checks as the global NL0 reader before dispatching foundation proofs or accepting a candidate. A rejected draft can be patched and resubmitted. The public freeze pins the reviewed mathematical foundations. NL0 receives this structured graph as a seed. Its global author can revise intermediate propositions and edges while preserving the original problem and the frozen foundation declarations.

List directly used B IDs on every consuming inference. The controller assigns working M/E labels and edges for these uses. Keep purely transitive prerequisites in their parent foundation's `uses`.
